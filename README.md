# ДЗ 5. Журнал корректировок с двумя осями времени

Реализуйте `Ledger` в одном файле `solution.py`, используя только стандартную библиотеку Python 3.12+. Сервис принимает корректировки счёта, иногда задним числом. Нужно отвечать не только «каков результат на дату», но и «что мы знали об этой дате после конкретной транзакции». Отзыв ошибочной записи меняет текущие ответы о прошлом, но не исторические ответы, полученные с прежней границей знания.

Это журнал денежных корректировок отдельных счетов, не система двойной бухгалтерской записи. Сумма по всем счетам не обязана равняться нулю. Все суммы целочисленные, в минимальных денежных единицах. Время здесь дискретное и не связано с системными часами. Сеть, файлы, сторонние пакеты, потоки и запуск дочерних процессов не нужны.

## Данные

Идентификаторы событий, счетов и целей: строки из 1–64 ASCII-символов `[A-Za-z0-9_.:-]`, регистр значим. Временные отметки: целые от 0 до `1_000_000_000` включительно. Сумма: ненулевое целое от `-10**12` до `10**12`. `bool` не является допустимым целым. Значения времени и суммы не преобразовываются из строк или дробей.

Есть ровно два формата событий, с точным набором ключей:

```python
{"id": "p1", "kind": "post", "account": "cash", "effective": 40, "amount": 120}
{"id": "r1", "kind": "retract", "target": "p1"}
```

`post` добавляет сумму на счёт с бизнес-временем `effective`. Принимать записи можно в любом порядке бизнес-времени. `retract` полностью исключает целевую запись из текущего представления, в том числе на прошлых бизнес-датах. Сам отзыв не имеет суммы и бизнес-времени. Целью может быть только `post`, уже принятый ранее или расположенный раньше в том же пакете. Ссылки вперёд, ссылки на отзыв и повторный отзыв другой записью запрещены. Идентичный повтор того же отзыва разрешён как повтор запроса.

Контейнеры входа: обычные встроенные `list` и `dict`, не пользовательские классы. Для любого нарушения описанного контракта поднимайте `ValueError`; текст сообщения свободный. Не требуется поддерживать циклические объекты, конкурентный доступ или переопределённые магические методы. Входные данные нельзя менять, а их последующее изменение вызывающей стороной не должно менять журнал.

## API

### `Ledger()` и `ledger.revision`

Новый журнал пуст, `revision == 0`. Ревизия является временем знания: номером успешно принятого пакета, добавившего хотя бы одно новое событие. Она растёт ровно на один на пакет, а не на запись. Свойство `revision` доступно для чтения.

### `ledger.apply(events) -> int`

`events` должен быть списком событий. Приёмка атомарна: либо все новые события приняты под одной новой ревизией, либо состояние полностью прежнее. Возвращается текущая ревизия. Пустой пакет и пакет только из повторов не повышают ревизию.

Идемпотентность определяется `id` и полным содержимым события. Порядок ключей словаря несущественен. Повтор уже принятого события с тем же содержимым не добавляется в историю. Совпадающие записи внутри одного пакета также принимаются один раз. Повтор с иным содержимым является конфликтом и отклоняет весь пакет, даже если раньше в нём были корректные новые записи. Сначала проверяется форма каждого события: например, `True` нельзя считать корректным повтором сохранённого целого `1`.

Правила целей проверяются слева направо по новым уникальным событиям. В пакете из новых записей и повторов новые получают одну общую ревизию; повторы остаются на исходных ревизиях. Неудачная попытка не резервирует `id` и не оставляет отзыв или пропуск ревизии.

### `ledger.balance(account, at, known_at=None) -> int`

Возвращает сумму активных `post` указанного счёта с `effective <= at`, видимых на ревизии `known_at`. По умолчанию это текущая ревизия. Явное `known_at=0` означает пустую историю. Допустимы только целые `0 <= known_at <= revision`, без `bool`; отрицательные и будущие ревизии являются ошибкой.

Запись видима, если ревизия её приёмки не больше `known_at`. Она активна, если на этой границе знания ещё не виден её отзыв. Отзыв убирает именно свою цель, а не весь счёт. Для корректного, но неизвестного счёта результат `0`. Ответ может выходить за диапазон отдельной суммы: используйте точные целые, без округления.

### `ledger.window(start, end, width, known_at=None) -> list[dict]`

Возвращает обороты, не накопленный баланс, в полуинтервале `[start, end)`. `start` и `end` являются допустимыми временными отметками, `start <= end`; `width` — целое `1..1_000_000_000`, без `bool`. `known_at` проверяется так же, как в `balance`, даже при пустом окне.

Разбейте диапазон на корзины `[start + k*width, min(end, start + (k+1)*width))`. Последняя может быть неполной. Набор счетов состоит ровно из счетов, у которых есть хотя бы один активный видимый `post` внутри всего окна. Нулевая сумма нескольких записей не удаляет счёт. Для каждой корзины выдайте строку для каждого такого счёта, включая строки с нулевыми оборотом и количеством. Сортировка: сначала `start` по возрастанию, затем `account` в обычном лексикографическом порядке Python.

```python
{"start": 0, "end": 10, "account": "cash", "amount": 120, "count": 1}
```

`amount` — сумма записей в этой корзине; `count` — число различных активных `post`, не число попыток приёмки и не число ненулевых итогов. Запись точно на `end` не входит. При `start == end` или отсутствии подходящих записей результат `[]`. Чтение не изменяет состояние.

### `ledger.checkpoint() -> dict` и `Ledger.restore(snapshot) -> Ledger`

Снимок — самостоятельный JSON-совместимый объект с точным форматом:

```python
{
    "version": 1,
    "revision": 2,
    "events": [
        {"revision": 1, "event": {"id": "p1", "kind": "post", "account": "cash", "effective": 40, "amount": 120}},
        {"revision": 2, "event": {"id": "r1", "kind": "retract", "target": "p1"}}
    ]
}
```

Порядок истории — порядок первой приёмки уникальных событий, внутри ревизии порядок пакета. Повторов в истории нет. Ревизии непустых групп начинаются с 1, идут подряд, не уменьшаются и заканчиваются указанным `revision`. Пустая история допустима только с `revision=0`. У снимка, каждой строки и каждого события точные наборы ключей; `version` должен быть целым `1`, не `True`.

Восстановление обязано проверить весь формат и воспроизвести правила приёмки по группам ревизий. Отклоняйте лишние поля, дубли событий, пропуски/перестановку ревизий, некорректные цели и любые недопустимые события. Валидный снимок должен после восстановления давать те же исторические ответы, идентичный снимок и ту же реакцию на дальнейшие запросы. Не возвращайте исходный экземпляр и не храните изменяемые ссылки на переданный или возвращённый снимок. Ошибка восстановления не должна затронуть ранее созданные журналы.

Это структурная проверка, не проверка авторства снимка. Изменённая сумма, которая всё ещё удовлетворяет контракту и не нарушает историю, допустима: цифровая подпись или контрольная сумма не требуются.

## Пример

```python
from solution import Ledger

ledger = Ledger()
ledger.apply([{"id": "a", "kind": "post", "account": "cash", "effective": 20, "amount": 7}])
ledger.apply([{"id": "b", "kind": "post", "account": "cash", "effective": 10, "amount": -2}])
assert ledger.balance("cash", 15, known_at=1) == 0
assert ledger.balance("cash", 15) == -2
ledger.apply([{"id": "c", "kind": "retract", "target": "a"}])
assert ledger.balance("cash", 30, known_at=2) == 5
assert ledger.balance("cash", 30) == -2
assert Ledger.restore(ledger.checkpoint()).checkpoint() == ledger.checkpoint()
```

## Объём и сдача

Проверяется до 2000 уникальных событий, до 64 счетов, до 200 запросов; в одном `window` не более 1000 корзин. Специальные индексы и заданная асимптотика не обязательны, но нельзя создавать массив по каждой временной отметке или бесконечно хранить повторные запросы. Поддержите большие интервалы с редкими событиями. Не требуется специально отклонять превышение этих нагрузочных границ.

Сдайте `solution.py`. Общий `test_smoke.py` проверяет только совместимость основного интерфейса и не является полной проверкой контракта. Дополнительные тесты допустимы. Импорт модуля не должен читать stdin, запускать демонстрации или писать файлы. Решение исполняется в изолированном Python-контейнере без сети: 256 МиБ, 1 CPU, 15 секунд, исходники только для чтения. Проверки не используют часы, случайную сеть или внешние данные.

## Рубрика

Максимум 20 баллов, итог `/10 = round(10 * сумма / 20, 1)`. Перечисленные подпункты независимы и дают по одному баллу при полном выполнении соответствующего требования; частично выполненный подпункт даёт 0. Невыполнение одного подпункта не обнуляет остальные. Примеры и открытые тесты не ограничивают проверяемые входы.

| ID | Критерий | Макс. | Подпункты для частичного зачёта |
|---|---|---:|---|
| input | Контракт и владение данными | 3 | Строгие формы и типы событий, включая диапазоны и `bool`; проверка всех аргументов запросов; независимость от изменений переданных событий и чистота чтений. |
| temporal | Две оси времени | 4 | Точные суммы и включительная бизнес-граница при поступлении задним числом; исторические ревизии, включая 0; ревизия на пакет и сохранение прежних границ знания; детерминированность и инварианты при перестановке независимых записей на заявленном объёме. |
| retry | Идемпотентность | 2 | Одинаковые повторы внутри/между пакетами и пустые пакеты не меняют историю; конфликтующее содержимое и некорректная форма повтора отклоняются. |
| atomic | Атомарная приёмка | 3 | Полный откат после поздней ошибки формы; полный откат после позднего конфликта `id`; полный откат после ошибки цели, включая возможность исправленного повторного запроса. |
| retract | Отзывы | 3 | Точный текущий и исторический эффект отзыва; цель только существующий/более ранний `post`, не отзыв/будущее; один отзыв на цель с допустимым идентичным повтором. |
| window | Оконная проекция | 2 | Полуинтервалы, неполная последняя корзина, количество и плотные нулевые строки выбранных счетов; историческая видимость, отзывы, сортировка и инвариант разбиения оборотов. |
| snapshot | Снимки | 3 | Точный формат и продолжение после round-trip; строгое отклонение структурно/семантически некорректной истории; отсутствие изменяемых общих ссылок при сохранении/восстановлении. |
